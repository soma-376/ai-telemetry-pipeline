# 0001. 프롬프트 원문을 다루지 않는다

## Status

Accepted

## Context

이 파이프라인은 CLI 코딩 툴(Claude Code · Codex)이 보내는 OTLP 텔레메트리를 조직 단위로 수집한다.
프롬프트 원문과 assistant 응답에는 사내 코드·자격증명·개인 정보가 섞일 수 있어,
서버 측에 원문을 보관하는 순간 유출 반경과 보관 책임이 함께 커진다.

개발자 로컬에는 원문을 보관하는 별도 경로가 이미 있다 — `telemetryctl` 이 로컬 저장소에만 원문을 남기고
상위 전달에서 제거한다(그 레포 ADR 0003). 상위(이 파이프라인)까지 원문을 받으면 그 경계가 무의미해진다.

결정하지 않으면 벤더 어댑터마다 원문 취급이 갈리고, 새 어댑터를 추가할 때마다 같은 논쟁이 반복된다.

## Decision

- 정규화 스키마의 `Prompt` payload 는 **길이(length)와 명령 이름(command_name)만** 싣는다.
- 프롬프트 본문·assistant 응답 원문은 어느 신호에서도 공통 스키마로 승격하지 않는다.
- 새 어댑터도 이 규칙을 따른다 — 원문 필드를 payload 에 추가하려면 이 ADR 을 먼저 개정한다.

## Alternatives

### A. 원문을 수집하고 서버 측에서 마스킹한다
- 장점: 의도(why) 분석 등 분석 자유도가 높다.
- 단점: 마스킹 누락이 곧 유출이고, 보관·접근 통제 책임이 파이프라인으로 넘어온다.
- 탈락 이유: MVP 의 프라이버시 경계(원문은 로컬에만)와 정면으로 어긋난다.

### B. 테넌트 설정으로 원문 수집을 켤 수 있게 한다
- 장점: 조직별 정책 유연성.
- 단점: 스키마·저장·마스킹 경로를 전부 이중으로 유지해야 한다.
- 탈락 이유: 수요가 확인되지 않은 상태에서 위험 표면만 넓힌다.

## Consequences/Tradeoffs

### Positive
- 프라이버시 경계가 운영 규칙이 아니라 **스키마로 강제**된다.
- 적재 데이터의 유출 반경이 통계 값 수준으로 좁아진다.

### Negative
- "의도(why)" 의 세밀한 라벨은 이 단계에서 만들 수 없다.
- collector 의 원본 아카이브(`file/*` exporter) 경로는 정규화 이전 페이로드를 그대로 담는다 —
  이 ADR 의 경계는 정규화 스키마에만 적용된다. 아카이브 경로의 프라이버시 집행 지점 정리는
  허브 계약 문서(`../docs/contracts/telemetry-ingest.md`)가 다룬다.

## Follow-up

- 원본 아카이브 경로에 대한 프라이버시 집행 지점을 허브 계약에 명시한다 (PROJ-80, 허브 반영 대기).
